# 个人求职 Agent 需求分析

日期为 2026-11-12。本文为完整重构的需求基线草案，依据本次用户描述、当前代码和仓库内已有验收记录编写。

## 1. 产品定义与分析结论

### 1.1 产品定义

面向独立求职者的个人 Agent。用户通过对话说明求职意向，系统持续维护求职条件，联网发现与核验机会，解释岗位适配程度，按约定提醒变化，并协助准备材料、填写申请和跟踪投递。

核心用户任务为以下七项。

1. 说明自己的情况和求职条件，并在后续对话中修改。
2. 找到此前不知道的公司和正在招聘的岗位。
3. 判断自己能否申请、岗位是否值得投入时间。
4. 持续关注新机会和重要变化，减少重复查看招聘网站。
5. 针对具体岗位准备真实、可用的申请材料。
6. 减少网申重复录入，并保留对提交的控制。
7. 记住投过什么、用了什么材料、进展如何、下一步做什么。

### 1.2 当前能否满足目标需求

**当前项目可以支持已有岗位上的部分求职执行流程，对用户提出的个人 Agent 场景只能部分满足。**

目前已经有官网采集、推荐、对话、记忆、材料审核、辅助填写、投递时间线、任务恢复和提醒基础。主要缺口集中在互联网主动发现、对话中的目标管理、目标级订阅，以及与岗位真实变化一致的通知。

现有材料也不足以证明真实用户已经持续获得收益。仓库记录了自动化回归和部分真实页面只读检查，真实人工耗时基线和完整真实网申演练仍有待验证。因此，本次分析可以判断功能覆盖与行为缺口，用户满意度、实际节省时间和真实渠道覆盖率仍需后续测量。

### 1.3 重构应保留的结果

完整重构需要保留上述七项用户能力、已有个人数据及可追溯关系。模块、表结构、框架、评分公式、工具数量和旧页面布局交由后续技术设计重新决定。

产品成功以用户能完成求职任务衡量。技术展示材料可以从实际实现和验证中提取。

## 2. 目标用户与需求依据

### 2.1 主要用户

优先服务正在找日常实习、暑期实习或应届岗位的学生，具备以下共同情况。

- 有方向和地域偏好，但对有哪些公司、哪些岗位开放了解有限。
- 资格受毕业时间、在校身份、实习类型、到岗时间和实习时长影响。
- 岗位分散在官网、招聘平台和社区帖子中。
- 会反复调整求职条件，连续多天或多周使用系统。
- 同时处理多个申请，需要保存材料、进展和提醒。

首个验收场景采用“2028 届、AI 产品经理日常实习、主要江浙沪、希望包含中小公司”。这组信息来自用户提供的示例对话，系统初始化时应等待真实用户提供个人条件。

社会招聘可复用其中部分任务，本轮详细规则和验收优先覆盖学生求职。

### 2.2 使用条件

- 延续单用户、本地使用的当前定位。
- 用户能够配置所需模型与搜索服务，按需使用浏览器扩展。
- 第一轮找岗位只要求必要的求职意向，简历可在后续补充。
- 定时检查依赖服务处于运行状态。界面应说明运行条件和漏跑后的处理方式。
- 外部通知需要用户启用有效渠道。站内结果、外部通知与实际送达状态分别可查。

### 2.3 需求的证据强度

| 依据 | 可以支持的判断 | 仍需验证的内容 |
|---|---|---|
| 用户明确提出找公司、推荐岗位、持续提醒、增加中小厂 | 发现机会和持续关注是主要需求 | 真实使用频率与渠道偏好 |
| 示例中的多轮条件补充 | 系统需要逐步理解并及时应用条件 | 追问节奏是否自然、默认解释是否符合预期 |
| 当前代码与功能文档 | 存在简历、填写和投递能力，需要纳入保留范围 | 哪些功能使用最多、哪些入口确实造成负担 |
| 历史验收记录 | 已有部分回归、恢复及页面扫描证据 | 当前版本实测、真实人工耗时和完整外部流程 |

本文件中的优先级和交互默认值属于产品建议，尚未经过独立用户访谈或长期使用观察。

## 3. 用户任务与产品价值

| 阶段 | 用户要完成的任务 | 主要困难 | 系统应提供的结果 |
|---|---|---|---|
| 明确目标 | 说清想找什么、自己的条件是什么 | 信息逐步补齐，条件可能变化 | 可查看、可修改且当轮生效的目标 |
| 寻找机会 | 找出可以考虑的公司和岗位 | 公司未知、来源分散、岗位过期 | 有来源和核验时间的候选清单 |
| 做出判断 | 知道能否投、为什么推荐 | 届别和实习要求复杂 | 逐项资格判断、匹配理由、待确认项 |
| 持续关注 | 及时知道新岗和重要变化 | 人工反复检查、容易错过 | 与个人条件一致且经过去重的提醒 |
| 准备申请 | 形成岗位相关的简历与答案 | 重复改材料、版本容易混淆 | 用户确认过的材料及岗位关联 |
| 执行申请 | 减少重复填写 | 多页表单、未知问题、登录与上传 | 可预览、可接管、可继续的填写过程 |
| 跟进申请 | 知道进度与下一步 | 信息散落、状态容易误记 | 可追溯时间线、行动和时间提醒 |

## 4. 现有能力与需求差距

本节为静态检查结论。存在实现表示有代码路径支持，其运行效果仍以对应验收为准。

| 用户需要 | 现有证据 | 满足程度 | 重构需要补齐的行为 |
|---|---|---|---|
| 自然语言交流与历史上下文 | pi-agent、流式回答、对话摘要与记忆检索 | 已有基础 | 把明确条件及时保存并作用于后续任务 |
| 对话建立或修改求职目标 | 画像 API、偏好表单、记忆候选 | 部分覆盖 | 完整的目标操作、个人事实与目标条件的一致读取 |
| 主动联网寻找岗位 | 已知公司官网适配器、自定义来源 | 部分覆盖 | 按意向执行网络搜索，发现未知公司和招聘入口 |
| 聊天搜索新机会 | `search_jobs` 查询本地 `JobPosting` | 存在关键缺口 | 联网发现与已有岗位检索均可用，结果说明检索范围 |
| 中小公司扩展 | 可以添加自定义来源 | 部分覆盖 | 从用户意向发现公司、加入关注并给出首轮结果 |
| 资格与适配判断 | 届别、招聘类型、方向、城市过滤和评分 | 部分覆盖 | 日期范围、实习细分、天数、时长及非技术职能的规则 |
| 多来源证据 | 岗位有来源、URL 和证据元数据 | 已有基础 | 同一岗位保留多个来源，字段冲突和更新时间可查 |
| 对话创建每日盯岗 | 间隔任务 API，聊天工具未暴露订阅操作 | 存在关键缺口 | 指定目标、时间、名单与渠道，支持修改和暂停 |
| 新岗去重提醒 | 站内 `JobChange`、飞书 `Notification` | 部分覆盖 | 两处提醒采用一致的业务含义，建立已展示基线 |
| 岗位材料准备 | 简历事实、逐条建议、预览、导出和版本 | 有实现支持 | 完整保留，并与新发现岗位衔接 |
| 辅助填写 | Chrome 扩展为常用入口，另有浏览器工作流 | 有实现支持 | 统一用户状态和接管体验，明确各入口支持范围 |
| 投递跟踪 | 时间线、实际材料、手工提交确认、下一步行动 | 有实现支持 | 完整保留，继续支持手工录入外部投递 |
| 恢复和历史数据 | Run/Step/Event、任务记录、备份恢复 | 有实现支持 | 重构后继续可查、可恢复，避免重复执行已完成操作 |
| 真实使用效率 | 固定任务测量模板、部分历史演练 | 证据不足 | 采集人工基线和完整任务结果 |

### 4.1 需要优先解决的问题

1. 用户说“帮我找”时，系统需要能够扩展已有岗位集合。
2. “我是 2028 届”“主要江浙沪”需要成为实际筛选条件，用户可检查保存结果。
3. 简历和完整画像确认的当前准备路径需要调整，使首次搜索可以更早开始。
4. 日常实习、暑期实习、特定届别项目和全体在校生招聘需要分别识别。
5. “建好了订阅”“加入了公司”必须有对应的实际配置与执行结果。
6. 提醒需要跟随岗位变化。当前飞书以推荐版本去重，站内岗位变化另有条件，用户接收结果可能存在差异。

## 5. 产品范围与功能取舍

### 5.1 核心功能保留清单

| 核心能力 | 完整重构必须交付的行为 | 可以重新设计的部分 |
|---|---|---|
| 对话与个人上下文 | 连续交流、条件维护、历史回看与纠错 | 记忆组织、摘要和检索实现 |
| 岗位发现与核验 | 联网搜索、已知来源检查、链接导入、详情证据 | 采集框架与适配器结构 |
| 资格判断与推荐 | 资格明确、未知项可见、理由有依据、用户可反馈 | 分数、排序算法与展示方式 |
| 订阅监控与提醒 | 创建、修改、暂停、恢复、基线、去重与状态查询 | 调度、通知实现与内部记录形式 |
| 简历和申请材料 | 导入、事实核对、逐条建议、编辑预览、版本与下载 | 编辑器、材料页面和文件生成实现 |
| 辅助填写 | 当前网页扫描、预览选择、人工接管、多页继续 | 浏览器执行入口及公共逻辑 |
| 投递与后续行动 | 手工和辅助投递记录、材料关联、时间线、下一步行动 | 看板形式、统计入口和内部阶段结构 |

### 5.2 保留为支撑能力

- 任务进度、中止、失败原因、重试和恢复。
- 个人资料与记忆的查看、修改和删除。
- 来源健康、受限渠道与最近检查情况。
- 模型配置与能力检测、基本调用费用记录。
- 数据备份、恢复以及旧数据迁移。
- 站内待办与外部提醒渠道配置。

### 5.3 按需提供的扩展

招聘邮件辅助识别、日历同步、详细统计复盘和 CSV 导入导出已有实现，可以按需启用。它们的接入失败应当独立呈现，找岗与手工跟踪仍应可用。迁移需要保留已有邮件关联、日历关联和历史数据。

面试训练、Offer 比较、独立职业规划等后续候选保持在待办中。当前需求分析优先完成七项核心任务。

### 5.4 冗余与复杂度的处理依据

用户已指出多次修改带来的冗余。下列为可从现有实现观察到的重叠，具体删除范围需要后续调用链检查。

| 重叠位置 | 可观察证据 | 需求层面的处理要求 |
|---|---|---|
| 用户条件 | `CandidateProfile`、`MemoryItem`、`MemoryCandidate` 和聊天上下文均可承载相关信息 | 生效的个人事实和目标条件有明确归属，修改后各入口一致 |
| 运行进度 | `AgentRun` 与 `TaskRun` 均保存状态、结果和错误 | 同一用户任务有一致的进度和恢复入口 |
| 提醒 | `JobChange` 与飞书 `Notification` 使用不同生成条件 | 站内和外部渠道共享一致的提醒决策 |
| 填写 | 扩展和浏览器工作流都支持扫描、准备或执行 | 用户能理解当前入口，切换与继续时状态一致 |
| 投递状态 | 投递实体及多类事件记录承担状态和历史 | 当前进展有明确计算依据，修改历史可以追溯 |
| 功能入口 | 对话、列表、材料页和设置包含相关动作 | 同一操作语义一致，详情入口围绕岗位和申请组织 |

数据模型数量和代码行数只能帮助定位维护成本。保留、合并或删除应当有对应的用户行为及调用证据。

## 6. 核心功能需求

各需求使用编号供后续技术设计、实现任务和验收引用。

### F1 对话、个人资料与求职目标

- **F1.1** 用户可以用自然语言建立目标，至少包含方向，其他条件可逐步补充。
- **F1.2** 个人事实和本次求职条件分别维护。毕业时间属于个人资料，目标城市和招聘类型属于求职目标。
- **F1.3** 明确自述和明确修改在本轮保存、生效，并返回实际保存的内容。含糊或冲突信息需要指出具体问题。
- **F1.4** 支持硬条件与偏好。“主要江浙沪”按地域偏好解释并明示，“只看江浙沪”按硬条件处理。
- **F1.5** 支持多个独立目标，后续短句修改作用于明确的当前目标。目标不明确时进行一次针对性澄清。
- **F1.6** 刷新、重启、切换聊天后，已保存条件仍可使用。用户能纠正或删除过时信息。
- **F1.7** 追问优先解决影响当前判断的缺失项。系统可以在信息不完整时先搜索，并说明当前采用的条件。

### F2 岗位与公司发现

- **F2.1** 按方向、地域和招聘类型联网寻找机会，包括此前未配置的公司。
- **F2.2** 支持公司官网、可访问的招聘平台和社区招聘信息。展示来源类型与链接。
- **F2.3** 支持用户给出公司或岗位链接，读取详情并加入当前目标。
- **F2.4** 支持扩大公司范围，例如增加中小公司。返回新增公司、关注理由、可用渠道和首轮检查结果。
- **F2.5** 未核实公司规模时说明依据不足，公司进入关注名单后继续检查具体岗位。
- **F2.6** 一轮搜索展示执行时间、主要覆盖渠道及受限来源。结果较多时支持继续查看。
- **F2.7** 部分来源失败时保留已获得结果，并给出可处理的失败原因。
- **F2.8** 无结果时说明哪些条件和来源已被检查，用户可以调整范围或继续关注。

### F3 岗位证据、资格与推荐

- **F3.1** 每个岗位至少保存公司、标题、招聘内容、来源链接和最近核验时间。其他字段允许未知。
- **F3.2** 区分发布日期、刷新日期、首次发现时间、核验时间和明确的截止日期。
- **F3.3** 资格逐项返回符合、不符合或未知，覆盖毕业条件、招聘类型、城市、到岗日期、每周天数和时长。
- **F3.4** 识别指定届别、届别范围、准确毕业日期区间和全体在校生等不同要求。
- **F3.5** 推荐说明方向相关性、已确认条件、个人优势和待确认项，关键判断附来源证据。
- **F3.6** 用户未提供到岗条件时，展示岗位要求并标注个人信息缺失。资格明确不符的岗位可查询原因。
- **F3.7** 同一岗位多渠道出现时关联来源并去重。编号、地点或业务团队不同的岗位需要保留区别。
- **F3.8** 详情无法访问、来源冲突、关闭状态未知时展示相应状态。官网明确关闭的结果及时更新。
- **F3.9** 公司级招聘项目与具体岗位的资格分别核验，投递入口和信息来源可以分别展示。
- **F3.10** 用户可以标记想投、暂缓、不感兴趣并恢复。后续排序和提醒遵守这些决定，相关规则可查。
- **F3.11** AI 产品等职能按相应职责评价。推荐规则随目标选择，避免所有岗位共享固定技术方向门槛。

### F4 持续监控与提醒

- **F4.1** 用户可以通过对话创建订阅，关联目标、关注公司、执行时间、时区和通知渠道。
- **F4.2** “每天早上”采用可见默认时间。本文建议 Asia/Shanghai 09:00，创建结果展示下一次执行时间。
- **F4.3** 支持立即检查、调整公司、修改时间、修改目标、暂停和恢复。修改后返回实际配置。
- **F4.4** 创建订阅时记录已展示岗位基线。同一岗位被重复采集、跨渠道发现或重新评分时保持去重。
- **F4.5** 用户要求“有新岗提醒”时默认只启用新匹配岗位事件。截止、重新开放和资格变化提醒分别可配置。
- **F4.6** 截止提醒依赖明确日期。公司批次时间展示其适用范围。
- **F4.7** 增加公司后完成新增范围的首轮检查，结果展示后纳入基线和后续监控。
- **F4.8** 无符合订阅的变化时更新检查记录，保持用户通知安静。
- **F4.9** 展示上次检查、上次成功、覆盖情况、下次执行和渠道状态。持续失败或需要登录时给出一次待处理提示。
- **F4.10** 服务重启后保留订阅，错过的周期合并补查，后续回到约定时间。
- **F4.11** 生成提醒与发送状态可追溯。失败发送可重试，发送结果未知时如实记录。
- **F4.12** 执行期间条件发生变化时，发送前依据最新条件复核。已暂停的订阅停止后续通知。
- **F4.13** 到期或已投递岗位仍能按用户关注策略跟进，同一岗位命中多个目标时合并提醒并说明原因。

### F5 简历与申请材料

- **F5.1** 保留 PDF、DOCX、Markdown 和纯文本简历导入，支持多版本、活动版本和附件管理。
- **F5.2** 用户能检查并修正提取的个人资料，确认可用于申请的事实。
- **F5.3** 围绕指定岗位生成具体修改建议，用户逐条采纳、编辑或保留原文。
- **F5.4** 建议和申请答案以已确认资料为依据。缺少经历或技能时提出需要补充的信息。
- **F5.5** 支持最终预览、保存、下载和上传自行准备的岗位材料。
- **F5.6** 基础简历或 JD 改变后提示核对旧建议，保留历史材料。
- **F5.7** 实际投递关联所用材料版本和答案，之后仍可追溯。

### F6 辅助填写与用户接管

- **F6.1** 用户可以从岗位或显式申请 URL 开始填写，支持当前网页扫描和预览。
- **F6.2** 展示拟填写、已有、缺失和需单独授权的字段。用户选择后执行，已有值按用户选择处理。
- **F6.3** 遇到登录、验证码、无法确定的必填题和页面变化时说明接管位置，补充后可以继续。
- **F6.4** 支持跨页扫描、暂存及重启后继续，显示已完成和待处理内容。
- **F6.5** 文件上传和最终提交按入口实际能力由用户操作，涉及系统代执行时取得绑定当前申请的明确确认。
- **F6.6** 填写进度、提交结果和投递记录分别保存。结果未知时提供核对入口。
- **F6.7** 用户可以手工完成整个网申，再补充投递记录和实际材料。

### F7 投递跟踪与每日行动

- **F7.1** 支持手工创建和更新申请，包括系统外发现的岗位和 JD 暂缺的申请。
- **F7.2** 保存公司、岗位、申请链接、投递时间、实际材料和进度事件。
- **F7.3** 保留重复阶段、跳级、自定义阶段和日期纠错的表达能力，当前进展与历史一致。
- **F7.4** 支持下一步行动、截止时间、笔试面试安排及完成标记，区分未来预约和已完成事件。
- **F7.5** 聚合待处理任务、新机会、到期行动和未确认结果，直接进入对应操作。
- **F7.6** 按需接入招聘邮件和日历。邮件无法唯一关联、内容冲突或结论不确定时提供人工核对。
- **F7.7** 列表搜索、筛选和分页覆盖完整记录，加载失败保留已加载结果并可重试。

## 7. 端到端验收场景

### 场景 A 从空白开始找实习

| 步骤 | 用户输入或操作 | 可观察结果 |
|---|---|---|
| 1 | 帮我找 AI 产品经理实习 | 建立初步目标并开始联网检索，展示关键缺失项 |
| 2 | 我是 2028 届 | 保存毕业信息，当轮重算资格，指出结果变化 |
| 3 | 日常实习，主要江浙沪 | 保存实习类型和地域偏好，江苏、浙江、上海均被覆盖 |
| 4 | 查看推荐 | 每项有来源、核验时间、推荐理由和未知条件 |
| 5 | 每天早上查，有新岗提醒 | 返回已创建订阅、具体时间、时区、渠道和下一次执行 |
| 6 | 加一些中小厂 | 展示新增公司和首轮检查结果，已有订阅同步更新 |
| 7 | 再次检查，数据无变化 | 保留检查记录，无重复新岗通知 |
| 8 | 关闭并重启应用 | 目标、基线、订阅和结果仍可查，补查规则生效 |

测试可使用有可控变更的来源验证去重和新增逻辑，再用真实只读搜索核对覆盖情况。真实岗位日期和开放状态随检索时刻记录。

### 场景 B 从推荐进入投递

1. 用户选择岗位并标记想投，查看完整 JD 和资格证据。
2. 导入或选定简历，检查事实并获取岗位修改建议。
3. 采纳部分建议、编辑内容，预览并保存材料版本。
4. 打开申请页面，核对填写预览后执行。
5. 未知必填题触发接管，用户补充后继续下一页。
6. 用户暂存并重启，恢复到同一申请并核对当前页面。
7. 用户完成官网提交，确认实际所用材料，投递时间线据此更新。
8. 登记面试安排与下一步行动，从每日待办继续跟进。

### 场景 C 边界与失败

| 输入或状态 | 预期行为 |
|---|---|
| 岗位要求 2026 届及以后，用户为 2028 届 | 毕业年份判断通过，其他条件分别判断 |
| 岗位限制准确毕业月份，用户只有届别 | 提示补充毕业时间并保留待确认结果 |
| 岗位要求每周 5 天，用户未提供天数 | 展示要求与未知项 |
| 同一岗位同时出现在官网和社区 | 关联来源，仅产生一次对应提醒 |
| 公司招聘项目面向 2028 届，具体岗位要求不同 | 依据具体岗位判断，展示项目与岗位信息 |
| 页面发布时间晚于检索时刻或日期互相矛盾 | 标记日期异常，保留原文与核验结果 |
| 某平台需要登录 | 标记受限，继续处理其他可访问来源 |
| 明确关闭或截止日期已过 | 更新岗位状态，停止作为当前开放岗位推荐 |
| 全部来源失败 | 本轮记录失败，历史结果保留原核验时间 |
| 用户修改城市或暂停订阅 | 发送前复核条件，后续调度和提醒遵守新配置 |
| 无模型或无搜索能力 | 显示当前能力，提供已有数据和手工操作入口 |
| 外部通知发送超时 | 记录送达未知，站内保留结果并展示处理状态 |

## 8. 信息组织与交互要求

### 8.1 主要入口

建议围绕对话、岗位、申请和个人资料组织主入口，首页聚合当日待办。设置集中放连接、运行环境和备份。具体页面数量由后续交互设计决定。

### 8.2 对话输出

- 目标修改后展示已保存条件及其适用目标。
- 岗位结果展示可执行信息，并提供查看详情、关注、忽略、准备材料和申请入口。
- 订阅操作后展示实际配置，可直接编辑、立即检查或暂停。
- 长任务持续展示进度，完成、部分完成、失败和等待用户具有清晰含义。
- 用户询问进度时读取实际运行记录，回答后可继续当前任务。

### 8.3 减少使用负担

- 同一信息在聊天、表单、推荐和提醒中保持一致。
- 首次搜索无需完成所有设置和简历资料。
- 常用操作在当前岗位或申请中完成，相关详情按需展开。
- 保存、发送和提交等操作完成后，状态有据可查。
- 技术评分、Token、工具步骤等细节按需查看，主要结果使用求职者熟悉的表达。

## 10. 数据保留与迁移要求

完整重构的验收包含已有数据迁移。

- 保留原始简历、确认事实、用户修正、附件、岗位材料和历史版本。
- 保留岗位、来源链接、推荐依据、关注和排除决定。
- 保留投递、实际材料关联、时间线、日期修正和下一步行动。
- 保留用户条件、有效记忆、对话历史和已有订阅配置。
- 保留通知历史和已展示信息，迁移后避免把已有岗位集中作为新岗重发。
- 未完成任务迁移为明确的可继续、需重新扫描或待用户处理状态，并保留历史。
- 已有间隔任务延续原约定，用户调整时再转换为新的时间配置。
- 邮件和日历等可选连接保留关联，恢复连接后能识别已有记录。
- 迁移前备份，使用副本核对数量、文件可读性、关键关联和代表性任务，再切换实际数据。

旧代码和旧接口的保留周期属于后续迁移设计。数据及核心用户行为的连续性纳入本需求。

## 11. 优先级与交付边界

优先级表示实施顺序。完整重构交付需要同时覆盖 P0、P1 和数据迁移。

| 优先级 | 范围 | 完成依据 |
|---|---|---|
| P0 | 目标对话、联网发现、核验推荐、公司关注、订阅与去重提醒 | 场景 A 和相应失败场景可重复通过 |
| P1 | 材料、辅助填写、投递跟踪、每日行动、历史数据迁移 | 场景 B、恢复及迁移检查通过 |

建议先跑通 P0 的完整用户流程，再把 P1 的保留能力接入。技术架构设计需要同时考虑两阶段，避免完成找岗后才发现材料和申请缺少关联。

## 15. Muse personal agent 能力借鉴

整理于 2026-11-12，参考对象为 Meta Muse。以下依据官方公开说明与当前仓库静态实现，记录产品借鉴和后续候选。当前重构优先级继续按第 11 节执行，新增候选在对应核心流程具备后评估交付。

### 15.1 能力拆解与项目落点

| 能力 | Muse 公开说明 | 项目已有基础 | 值得补齐的行为 |
|---|---|---|---|
| 持续目标管理 | 长期目标拆成计划，跟踪进展 | 单次 AgentRun 的 goal、定时工作流，重构已规划 Goal | 目标关联多个任务和申请，维护阶段安排、时间投入及下一行动 |
| 事件驱动推进 | 按时间和相关事件后台工作，筛选值得通知的结果 | 每日行动、岗位变化、邮件同步、调度 | 事件发生后准备具体成果，再判断是否需要用户关注 |
| 个性化记忆 | 跨对话记忆用户信息，用于后续建议 | 事实候选、确认、冲突检测、摘要与检索 | 有效期内的阶段安排影响每日行动，确认偏好影响推荐 |
| 跨应用执行 | 连接应用，浏览网页并执行多步骤任务 | 招聘来源、浏览器扩展、邮件和日历连接 | 围绕同一目标串联发现、材料、填写与后续跟进 |
| 可交付成果 | 生成文档、PDF 和交互成果 | 岗位材料、简历版本、实际提交快照 | 形成可复用、可追溯的面试准备包和复盘记录 |
| 可控与透明 | 展示活动、权限，提供结构化审批 | Run/Step/Event、人工接管与审批 | 集中展示目标进展、阻塞原因、已完成成果和待确认动作 |

Muse 的目标、后台工作、记忆、成果及交互描述来自官方产品与设计文章。[产品介绍](https://about.fb.com/news/2026/09/introducing-muse-personal-ai-agent/)、[设计说明](https://muse.ai/blog/how-we-designed-muse)

Muse 的连接与浏览器执行采用独立控制和审批机制，其可借鉴原则为动作范围明确、执行可追溯、用户可接管。[安全与执行设计](https://muse.ai/blog/security-and-safety-for-ai-agents-our-approach-with-muse)

### 15.2 建议的增量顺序

1. **事件到成果的首个流程。** 邮件连接可用后，从用户确认的面试通知生成准备包，汇总关联 JD、实际提交简历、时间与准备行动。检查申请关联准确性、材料完整性和用户采用情况。
2. **跨任务目标推进。** 在重构 Goal 与每日行动基础上增加阶段安排、可用时间和任务关联。面试临近、岗位截止或任务完成后更新行动建议，并展示调整依据。
3. **反馈与复盘复用。** 保留岗位接受／拒绝原因，向用户提出可审核的偏好更新。确认后作用于相似岗位排序和解释。面试复盘保存真实问题、困难点和项目证据，供后续准备引用。
4. **经验复用。** 延续来源解析策略修复和表单字段学习，让验证通过的策略与用户纠正服务于后续采集、填写，保留适用范围与来源。

上述顺序用于候选能力内部排序。联网发现、目标条件维护、订阅去重和申请数据迁移仍按既定重构阶段推进。

### 15.3 阶段安排与主动行动的产品约定

- 稳定个人事实、目标条件、阶段安排和具体申请行动各有明确归属。例如“这周准备面试”记录适用目标与有效期，到期后恢复原安排或提示重新确认。
- 明确的目标条件修改按 F1 当轮保存，从多次岗位反馈概括出的新偏好先展示依据，由用户确认后生效。
- 主动行动优先覆盖已确认面试、重点岗位截止和已关注 JD 变化。通知说明发生了什么、影响哪个目标、准备了什么，以及需要用户处理的动作。
- 后台检查复用订阅基线与去重规则，只有影响决策、产生可用成果或需要用户处理的变化才触发通知。
- 衡量候选效果时记录关联错误、重复提醒、准备耗时和成果采用情况，数值目标待真实基线后确定。

公开资料支持上述能力层面的借鉴。Muse 内部规划和记忆算法、当前项目的实际用户收益仍需进一步验证。
